# Reflection: #290 (guardrails §1.3: no user-entered strings in data-testid), 2026-11-13

**PR:** #295 (`autodev/290-testid-user-strings`)
**Shape:** docs-only.

## What went well
- The optional audit was cheap and useful. A grep for template-literal testids not keyed on an index gave 48 hits across `src/`, and every one keys on an enum value, a slug, a fixed field key, or a DB id. None is user-entered. So the rule describes the codebase as it stands, not a cleanup backlog.
- The rule names the boundary explicitly: slugs, enums and DB ids are app-generated, so they are fine. Without that line, a reader could take the rule to ban `flows-item-{id}`.

## Rule worth keeping
- When writing a guardrail, run the grep for existing violations in the same PR. A rule that silently has 10 violators is a rule nobody trusts.
