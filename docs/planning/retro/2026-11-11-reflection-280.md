# Reflection: #280, Preferences section in /settings (2026-11-11, /autodev)

- **What shipped:** `PreferencesSection` adds radiogroups for the composer and pose-detail layers, plus switch chips for the 7 custom fields. It reads `migratePreferences(browserStorage())` through `useClientValue`. `writePreference` in `preferences.ts` is the one write path, and #281 will reuse it. `browserStorage()` sits in its own file so that `preferences.ts` keeps its "no global access" contract.
- **Decision:** I gave `preferences` its own `SectionId` after `appearance` and did not nest it inside Appearance. `SettingsClient` tests assert that rendered `settings-section-*` ids equal the index links, and a nested section would have broken that invariant. As a result, FR-002's enumerated order no longer lists every section. The owner may want the spec line amended to read "…appearance, preferences, notifications…".
- **Pattern:** `useClientValue` needs a primitive or a stable value. The custom-field record therefore travels as a JSON string and is parsed in `useMemo`. Returning `migratePreferences(...).poseDetailCustomFields` directly would re-render forever.
- **Red proof:** the red run failed because the modules could not be resolved (the new files did not exist), not on an assertion. That is weaker evidence than an assertion failure.
