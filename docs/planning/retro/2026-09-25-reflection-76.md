# Reflection — Issue #76

**Issue:** branch-coverage gate is red on main — 99.42% vs 100% threshold in
`datadog-sync.mjs`

## What changed

Two uncovered branches in `scripts/lib/datadog-sync.mjs`. One was real and
testable: `extractScopedQueries`'s `JSON.stringify(value) ?? ''` fallback,
covered with a test calling it with `undefined` (mirroring the existing
`extractMetricNames(undefined)` test for the sibling function). The other —
`quietMetricNames`'s `fragment.match(...) ?? []` + `if (metric)` guard — was
provably unreachable: every fragment `extractScopedQueries` emits already
conforms to the exact shape the second regex expects, so the match can never
fail. Removed that dead fallback instead of writing a test around unreachable
code.

## Pattern / anti-pattern

- When a "missing coverage" issue names two branches, don't assume both need
  a test. Trace the actual call graph first — one function's output can make
  a downstream defensive check provably dead, in which case deleting it (per
  "don't add error handling for scenarios that can't happen") is the more
  honest fix than writing a synthetic test just to make coverage tooling
  happy, or a suppression comment that hides the fact the branch is genuinely
  unreachable rather than describing why.
- The issue itself had already done this analysis and offered both paths
  ("add tests, or a documented ignore if provably unreachable") — worth
  reading an issue's own reasoning fully before defaulting to "just add a
  test for every uncovered line."

## Codebase insight

This gate is global (`vitest.config.ts`'s coverage threshold applies
repo-wide, not just to the friction-engine/validator-lite files the
constitution mandates), so any file's coverage regression blocks every PR's
gate regardless of what that PR touches — worth remembering when a gate
failure looks unrelated to the change at hand: check whether it's pre-existing
on `main` before assuming the PR caused it.
