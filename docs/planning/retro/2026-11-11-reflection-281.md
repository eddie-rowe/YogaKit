# Reflection — #281 compose + pose detail through migratePreferences (2026-11-11, /autodev)

- **What shipped:** `useStoredPreference(key)` (`src/lib/settings/use-stored-preference.ts`) is now the one read/write path for the three writable preferences. It reads `migratePreferences(browserStorage())` through `useClientValue` (JSON snapshot so objects stay stable), and writes through `writePreference` after applying the change in memory. ComposeClient, `useDetailLayer`, and PreferencesSection all use it. The per-surface key constants and raw `localStorage` calls are gone; a source-grep test keeps it that way.
- **Real bug found in browser validation of #280:** on the preview, `/compose` always rendered `simple` after a reload, even with `krama-compose-layer=advanced` stored. The `useState(() => localStorage…)` initializer hydrates against the server's markup, so the stored value never showed. jsdom tests can't see this (no SSR/hydration). Moving to `useSyncExternalStore` fixes it by construction; it is confirmed only on this PR's preview.
- **Legacy mapping moved into the migration:** compose used to read a stored `'custom'` as `'advanced'`. `migratePreferences` now does the same (it used to drop it to `simple`), so /settings and compose agree.
- **Review follow-ups folded in:** the #283 reviewer flagged two issues. When storage throws, a click wrote nothing, so the control looked dead (FR-007). And the custom-fields switch row had no group label. The in-memory override fixes the first, and `role="group"` + `aria-labelledby` fixes the second.
- **Stacked branch:** built on `autodev/280-preferences-section` because it needs `writePreference`. It gets rebased onto main after #283 merges.
