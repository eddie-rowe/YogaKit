# Reflection: #296 (RULE-H6 engine-isolation scanner: dynamic import() and require()), 2026-11-14

**PR:** #298 (`autodev/296-engine-isolation-scanner`), merged (squash `edea383`)
**Shape:** test-only. No file under `src/` changes.

## What went well
- Red was real. The planted `import()` and `require()` cases failed on the old regex with an empty violations list, which is exactly the gap the issue describes.
- The comment case could not fail against the old regex, because that regex matched the `from '…'` tail directly. It was seeded separately by switching off comment stripping in the shared helper. A case that cannot go red against the old code needs its own seed, or it proves nothing.
- Extracting the walk as `violationsFrom(entries, read, exists)` made every planted case a three-line test.

## What went wrong
- The first push moved the regex comment strip from #293 into the shared helper unchanged. The review then showed it could hide a real import: `const A = 'image/*'` deletes code up to the next comment close, and `'//cdn'` cuts the rest of its line. The old engine scanner did no stripping, so for the engine guard this would have been a regression shipped inside a PR meant to close a gap.
- The helper's own comment claimed a `//` in a string "can only drop text after a specifier, never the specifier itself". That was false, and it had been on `main` since #293.

## Rules worth keeping
- **Strip comments with a lexer, not a regex.** A regex cannot tell a comment marker inside a string from a comment. This supersedes the 2026-11-13 rule "strip comments before scanning", which was right about the goal and wrong about the tool.
- **A scanner's safety claim in a comment is a test waiting to be written.** If the comment says "this can never hide X", plant X.
- **The independent review earned its cost here.** It ran the regex against inputs. Reading the diff would not have found either hole.

## Left open
- `FETCH` misses `globalThis.fetch(`, `XMLHttpRequest`, `WebSocket` and `sendBeacon`.
- `.js`/`.mjs` files and `./foo.js` → `foo.ts` specifiers are not walked.
- Non-literal specifiers and quoted names inside an import list cannot be seen by a text scanner. Both limits are written in `import-scan.ts`.
- `docs/krama-guardrails.md` lists `account-menu` beside `account-menu-name`, which reads as a prefix-rule violation. Not checked further; out of scope for this sweep.
