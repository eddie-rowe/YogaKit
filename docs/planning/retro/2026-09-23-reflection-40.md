## Judgment calls a reviewer should double-check

1. **T043 component boundaries.** The split follows one rule: each piece owns one
   visually/functionally distinct region of the screen (title+save, layer chips,
   search+add, toolbar+total, warnings, the DnD list, phases), and every piece is a
   pure function of props — no piece reaches into storage, routing, or
   `localStorage` itself. `ComposeFlowList` is the one component that still takes a
   fairly wide prop surface (9 props) because it's the thing that actually needs
   `sensors`/`onDragStart`/`onDragEnd` alongside the per-item callbacks; I considered
   splitting the empty-state message out further but judged that would be a
   component with no independent reason to change, so left it inline. Reasonable
   alternative boundaries exist (e.g. folding `ComposeToolbar` into `ComposeWarnings`
   since they're adjacent in the layout) — I kept them separate because they answer
   different questions ("what can I do next" vs. "what's wrong").
2. **T043 DOM-preservation mechanism.** Several of the new components
   (`ComposeHeader`, `ComposeWarnings`) return a React Fragment wrapping multiple
   sibling elements, relying on the fact that Fragments don't add a DOM node — so
   the parent's `space-y-6` Tailwind spacing (a `> * + *`-style child selector)
   still applies exactly as before. This is correct React/DOM behavior, not a
   trick, but it's the kind of thing worth a second look if the layout ever seems
   off after a future edit to one of these components.
3. **T048 — no code change.** I took the issue's own instruction literally here:
   tests-first surfaced that scroll preservation across a *button* reorder is
   already correct, because (a) `sortedItems.map(item => ...)` keys each row on
   `item.id` (stable across a reorder — React reorders the existing DOM nodes
   rather than remounting them) and (b) grepping `src/app/compose` and
   `src/components/compose` turns up zero calls to `scrollTo`/`scrollIntoView`
   anywhere in the reorder path. I sanity-checked the test wasn't vacuous by
   temporarily injecting a fake `window.scrollTo(0, 0)` into the test harness's
   `moveItem` and confirming the spy assertion failed, then reverted the injection
   before committing. **What I did not verify**: the drag-triggered path
   (`handleDragEnd`) end-to-end in a real browser — `@dnd-kit`'s pointer sensor
   doesn't activate under jsdom, so the smoke test only exercises the button path
   directly. The drag path shares the same key-stable list and the same absence of
   any scroll call, so the same reasoning should hold, but a reviewer who wants
   higher confidence on the drag case specifically should watch it in a live
   browser (walk2-compose.spec.ts's existing button-reorder assertion already
   covers the button path in a real browser; nothing today added drag coverage
   there, and the issue didn't ask for a new Playwright spec).
4. **Orchestrator checkpoint.** Partway through T043 the orchestrating session's
   stop-hook fired on untracked files and committed my in-progress disk state as
   `a8b0413` ("[WIP] ... Background build agent continues on this branch"). I
   mistook this for a second, independently-running agent on the same branch (the
   `ListAgents` entry and the WIP commit message both read that way) and paused to
   message both it and the orchestrator before continuing — the orchestrator
   confirmed there was no second agent, just its own hook. No harm done (the
   checkpointed state was exactly my own in-progress work, which I then finished
   cleanly on top of), but it cost a coordination round-trip. Flagging in case the
   hook's commit message wording is worth revisiting — "background build agent"
   reads as a peer process, not a checkpoint of the same session.
