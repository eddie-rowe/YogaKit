# Reflection — Issue #67

**Issue:** db-types-check: retry `supabase start` on ghcr.io rate-limit, job
dies before the drift check runs

## What changed

Wrapped the `supabase start` step in `.github/workflows/ci.yml`
(`db-types-check` job) in a bounded retry loop (3 attempts, 10/20s backoff)
so a transient `ghcr.io toomanyrequests` image-pull failure doesn't kill the
job before `scripts/db-types-check.sh` — the actual drift check — ever runs.
A persistent failure (bad migration, real schema error) still fails the job
after the third attempt; the retry only covers the image-pull step.

## Pattern / anti-pattern

- CI-only workflow-YAML fixes don't fit the "tests first, red then green"
  loop this routine otherwise requires — there's no vitest surface for a
  GitHub Actions step, and `act`/Docker aren't available in this headless
  run. Verification here is the full local gate (green) plus reading the
  diff against the acceptance criteria, not a red/green test pair. Worth
  naming explicitly in the routine doc so future runs don't stall looking
  for a test to write.
- This is the second time the identical `ghcr.io toomanyrequests` signature
  has shown up in loop artifacts (first noted, unfixed, in PR #66's own
  handoff). Filing it as its own issue rather than re-discovering it per-PR
  worked — worth keeping as the pattern for recurring CI flake signatures.

## Codebase insight

`db-types-check` still isn't a required status check (tracked separately in
issue #65 / branch protection), so this fix reduces noise rather than
unblocking merges directly — merges were never blocked by this failure, only
the drift-check's own signal was being lost.
