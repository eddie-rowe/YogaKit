# /pr - Create Pull Request

Create pull request: commit, push, create PR, update issue status.

[Extended thinking: Execute PR creation steps. Read context from GitHub issue comments (/plan, /dev, /validate) to build comprehensive PR description. Commit any uncommitted files (reflection reports, logs). Quality gates already passed in /dev and /validate.]

## Usage
```
/pr <issue_number>
```

## Examples
```
/pr 65
/pr 123
```

## Execution

When invoked with `/pr <issue>`, execute these steps:

1. **Validate Input**
   ```
   # If no argument provided, show error:
   "❌ Please provide an issue number"

   # Parse issue number from argument
   ```

2. **Begin PR Creation**
   **Output:**
   ```
   🚀 Creating PR for issue #{issue}...
   ```

3. **Fetch Context from GitHub**

   ```bash
   # Get issue with all comments
   gh issue view {issue} --comments
   ```

   **Extract from comments:**
   - **From `/plan` comment**: Architecture decision, implementation steps
   - **From `/dev` comment**: Branch name, files changed, summary
   - **From `/validate` comment**: Test results, validation status

   ```bash
   # Get git diff summary
   git diff main...HEAD --stat
   git log main..HEAD --oneline
   ```

4. **Check Documentation Freshness**

   Compare the PR's changes against existing docs:
   ```bash
   # List docs that might be affected
   ls docs/*.md docs/**/*.md 2>/dev/null
   ```

   Using the diff from step 3, evaluate each doc in `docs/` for staleness:
   - `docs/USER_JOURNEYS.md` — Do the changes add, remove, or modify any user-facing flow?
   - `docs/ARCHITECTURE.md` — Do the changes alter architecture, add services, or change data flow?
   - `docs/OBSERVABILITY.md` — Do the changes affect monitoring, logging, or alerting?
   - Any other `docs/*.md` — Does the content overlap with changed files?

   **If docs may need updates, output:**
   ```
   📄 Documentation check:
   The following docs may need updating based on this PR's changes:
   - docs/USER_JOURNEYS.md — {reason}
   - docs/ARCHITECTURE.md — {reason}
   ```

   Use AskUserQuestion to let the user choose: update now, skip, or mark as follow-up.

   - **If update**: Read the flagged doc(s), apply targeted edits reflecting the PR's changes, and leave them as uncommitted changes (step 5 will commit them).
   - **If skip**: Continue to step 5 without changes.

5. **Commit Any Remaining Uncommitted Files**

   Check for uncommitted files (logs, minor fixes, etc.):
   ```bash
   # Check for uncommitted changes
   git status --porcelain

   # If uncommitted files exist, stage and commit them
   if [[ -n $(git status --porcelain) ]]; then
       git add -A
       git commit -m "chore(#{issue}): add remaining session artifacts

       Includes any uncommitted files from development session.

       🤖 Generated with Claude Code"
   fi
   ```

6. **Push to Remote**

   ```bash
   # Ensure branch is pushed (may already be from /dev)
   git push -u origin HEAD
   ```

7. **Create Pull Request**

   Build PR description from issue comments:
   ```bash
   gh pr create --title "{type}(#{issue}): {title}" --body "$(cat <<'EOF'
   ## Summary
   {Brief overview from /plan comment}

   Closes #{issue}

   ## Implementation
   {From /dev comment - what was built}

   ## Changes
   {Key files and what changed - from git diff}

   ## Validation
   {From /validate comment - test results}
   - ✅ E2E tests passed
   - ✅ Validation checklist complete

   ## Review Focus
   {Key areas for reviewers - from /plan architecture decision}

   ---
   *Created by `/pr` from issue #{issue}*
   EOF
   )"
   ```

8. **Update Issue Labels**

   ```bash
   # Update labels
   gh issue edit {issue} --add-label "ready-for-review" --remove-label "in-progress"

   # Note: Project board status automatically set to "In Review" via GitHub automation
   # when PR is linked to issue (via "Closes #" in PR body)
   ```

9. **Post PR Comment to Issue**

   ```bash
   gh issue comment {issue_number} --body "$(cat <<'EOF'
   ## Pull Request Created

   **PR:** #{pr_number} - {pr_title}
   **Link:** {pr_url}

   ### Status
   - Branch pushed to remote
   - PR created with validation summary
   - Ready for review

   ---
   *Generated by `/pr` - Run `/review {pr}` to check status*
   EOF
   )"
   ```

10. **Complete PR Creation**
    **Output:**
    ```
    ✅ PR created!

    📋 Issue: #{issue}
    🔗 PR: {pr_url}
    📝 PR comment posted to issue
    📊 Issue status: In Review

    🤝 Handoff complete! CI/CD will run automatically.
       Notify reviewer that PR #{pr} is ready.

    💡 Next step: '/down' to stop your local development environment
    ```

## Success Criteria

- Changes committed with clear, conventional commit message
- PR created with comprehensive description
- Issue labeled "ready-for-review"
- Issue status set to "In Review" on project board
- PR linked to issue via "Closes #" reference
